Banco do Brasil

Este documento orienta o suporte na configuração do portador Banco do Brasil (código 001) para clientes que vão usar a cobrança via API do Sentus.

Visão geral​

  • Autenticação: OAuth2 client_credentials. O Sentus envia client_id/client_secret no header Authorization: Basic e os escopos (api.sentus.roles) separados por espaço.
  • Todas as chamadas levam Authorization: Bearer <token> e o parâmetro de query gw-dev-app-key (a developer_application_key da aplicação).
  • Cobrança não usa certificado digital (mTLS). Só o Extrato exige mTLS.
  • Operações suportadas no Sentus:
OperaçãoEndpoint BB
Emitir (registrar) boletoPOST /boletos
Consultar boletoGET /boletos/{id}
Listar boletosGET /boletos
Alterar boletoPATCH /boletos/{id}
Baixar boletoPOST /boletos/{id}/baixar
Extrato de conta corrente (mTLS)GET /conta-corrente/agencia/{agencia}/conta/{conta}
Webhook de cobrança (BB → Sentus)POST /bb/webhooks/cobranca/{tenantId}/{portId}/{portAuth}
Identificador do boleto

O {id} é o nosso número de 20 dígitos: 000 + convênio (7 dígitos) + número de controle (10 dígitos). Ex.: 00031285570000030000.

PDF do boleto

O BB não tem endpoint de PDF. O Sentus não gera PDF pelo banco: a impressão usa a linha digitável e o código de barras retornados no registro.

Pré-requisitos (cliente)​

Sem estes itens não é possível configurar

O cliente precisa ser cliente do BB, ter convênio de cobrança ativo e uma aplicação no Portal Developers enviada para produção. O BB não gera credenciais de produção para quem não é cliente.

  1. Convênio de cobrança ativo (7 dígitos), contratado no BB Digital PJ (Contratação de Serviço > Cobrança e Pagamentos > Contratar serviço) ou com o gerente.
    • Tipo de convênio para registro via API: 3 (Banco numera; cliente emite e expede) ou 4 (cliente numera, emite e expede). Outros tipos não registram por API, mas permitem listar, baixar e detalhar.
    • Modalidade: 1 – Simples ou 4 – Vinculada.
    • Carteira 17.
  2. Cadastro no Portal Developers BB por uma pessoa física (CPF, e-mail e celular validados).
  3. Aplicação criada no Portal com a API Cobranças (v2).
  4. Representante da empresa (com poderes cadastrados no BB) para assinar o Termo de Adesão no envio para produção.
Layout do boleto

Antes de emitir em produção, o BB exige validar o layout da ficha de compensação no Validador de Layout BB (Portal Developers). Use os dados reais do convênio, não os fictícios do sandbox.

Passo a passo no Portal Developers​

  1. Criar aplicação: Criar Nova Aplicação → nome, descrição e API Cobranças → Criar.
  2. Credenciais de teste: Detalhes da aplicação > Credenciais > Gerar credenciais. Baixar tudo (o BB não mostra de novo).
  3. Testar no sandbox (ver Ambientes).
  4. Enviar para produção: Detalhes da aplicação > Enviar para produção → CNPJ da empresa → contatos → conferir dados → assinar o Termo de Adesão.
  5. Credenciais de produção: Credenciais > Ambiente de produção > Gerar credenciais.
Atenção no envio para produção
  • Mais de um representante obrigatório ou quem está enviando não é representante: a aplicação fica em Aguardando aprovação e os representantes precisam aprovar no Portal (sino) ou no BB Digital PJ (área Pendências). Sem aprovação em 30 dias, é preciso criar outra aplicação.
  • Aplicação em estado Aprovada (e não Produção): o dono ou o time técnico deve clicar em Finalizar envio para produção nos detalhes da aplicação. Só depois as credenciais de produção podem ser geradas.
  • Gerar novas credenciais desativa as anteriores. Só a mais recente vale. Se o cliente gerar de novo, atualize o params do portador.
  • O Termo de Adesão é assinado a cada aplicação enviada para produção.

Parâmetros (params)​

Exemplo para Produção:

api.ambiente=PRODUCAO
api.url.auth=https://oauth.bb.com.br/oauth/token
api.url.cob=https://api.bb.com.br/cobrancas/v2/boletos
api.url.cobConsulta=https://api.bb.com.br/cobrancas/v2/boletos/{id}
api.url.cobListar=https://api.bb.com.br/cobrancas/v2/boletos
api.url.cobAlt=https://api.bb.com.br/cobrancas/v2/boletos/{id}
api.url.cobBaixa=https://api.bb.com.br/cobrancas/v2/boletos/{id}/baixar
api.url.extrato=https://extratos.mtls.api.bb.com.br/v2
api.webhookAuth=CHAVE_DEFINIDA_PELO_SUPORTE
api.sentus=true
api.sentus.grantType=client_credentials
api.sentus.roles=cobrancas.boletos-requisicao cobrancas.boletos-info
api.appKey=COLE_A_DEVELOPER_APPLICATION_KEY
api.client_id=COLE_O_CLIENT_ID
api.client_secret=COLE_O_CLIENT_SECRET

Exemplo para Homologação (Sandbox): mesmas chaves com sufixo Hom e hosts hm:

api.ambiente=HOMOLOGACAO
api.url.authHom=https://oauth.hm.bb.com.br/oauth/token
api.url.cobHom=https://api.hm.bb.com.br/cobrancas/v2/boletos
api.url.cobConsultaHom=https://api.hm.bb.com.br/cobrancas/v2/boletos/{id}
api.url.cobListarHom=https://api.hm.bb.com.br/cobrancas/v2/boletos
api.url.cobAltHom=https://api.hm.bb.com.br/cobrancas/v2/boletos/{id}
api.url.cobBaixaHom=https://api.hm.bb.com.br/cobrancas/v2/boletos/{id}/baixar
api.url.extratoHom=https://extratos.mtls.api.hm.bb.com.br/v2
api.webhookAuth=CHAVE_DEFINIDA_PELO_SUPORTE
api.sentus=true
api.sentus.grantType=client_credentials
api.sentus.roles=cobrancas.boletos-requisicao cobrancas.boletos-info
api.appKey=COLE_A_APP_KEY_DE_TESTE
api.client_id=COLE_O_CLIENT_ID_DE_TESTE
api.client_secret=COLE_O_CLIENT_SECRET_DE_TESTE
Atenção
  • {id} é literal: o Sentus substitui pelo nosso número.
  • O Sentus escolhe a URL pela situação do portador: Homologação usa as chaves *Hom; Ativo usa as de produção. Preencha as duas famílias se o cliente vai passar pelas duas etapas.
  • api.sentus.roles leva os escopos separados por espaço. Os escopos precisam estar habilitados na aplicação do Portal; se não estiverem, o BB recusa o token.
  • A appKey e as credenciais de teste e produção são diferentes. Não misture.
  • Sem api.appKey, a emissão falha com "App Key não configurada para o ambiente".
  • Sem api.url.cob* do ambiente ativo, a operação falha com "Url de ... inválida".
  • O extrato só funciona com o certificado mTLS do cliente (.crt e .key no zip do portador) e a URL api.url.extrato.

AlterarUma alteração por chamada

ExtratoPeríodos de até 31 dias por chamada (o Sentus divide), até 5 anos para trás, 120 registros por página; 404 = sem lançamentos

Webhook de cobrança (opcional)​

O evento é a baixa operacional (pagamento) de um boleto. O Sentus recebe em:

POST https://<host-sentus>/bb/webhooks/cobranca/{tenantId}/{portId}/{portAuth}
ParâmetroOrigem
tenantIdIdentificador do tenant do cliente
portIdID do portador cadastrado
portAuthValor que o suporte define em api.webhookAuth no params do portador. Precisa ser idêntico ao da URL; se faltar ou diferir, o Sentus rejeita

O BB envia uma lista de notificações; o Sentus sincroniza cada título pelo campo id (nosso número) e responde 200.

Cadastro do evento no BB​

  1. A aplicação precisa estar em Produção (a aba Eventos só aparece nesse estado).
  2. Portal Developers → aplicação → card Webhook → Eventos → Cadastrar novo evento.
  3. Informar o convênio (identificador), a URL do servidor (a do Sentus acima) e um e-mail → Salvar.

Erros comuns​

SintomaCausa provável
400 ao gerar o tokenEscopo não habilitado na aplicação, escopos mal separados (espaço) ou credencial de outro ambiente
401 UnauthorizedToken expirado, credenciais antigas (foram regeneradas) ou appKey de outro ambiente
"App Key não configurada"Falta api.appKey no params
"Url de ... inválida"Falta a chave api.url.* do ambiente ativo
Erro ao alterar/baixar logo após emitirO BB só aceita depois de 30 minutos
404 na listagemFiltros sem resultado (não é falha de conexão)
Boleto recusado em produção com dados de testeCNPJ/CPF fictícios do sandbox não valem em produção
Credenciais de produção indisponíveisAplicação em Aprovada (finalizar envio) ou Aguardando aprovação (falta assinatura)
Webhook não chegaEvento não cadastrado, aplicação fora de Produção, mTLS/porta no servidor ou portAuth diferente de api.webhookAuth
