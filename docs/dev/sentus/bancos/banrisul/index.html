Banrisul

Este documento orienta o suporte na configuração do portador Banrisul (código 041) para clientes que vão usar a cobrança via API do Sentus.

Visão geral​

  • Autenticação: OAuth2 client_credentials, escopo boletos.
  • Todas as chamadas levam Authorization: Bearer <token> e o header bergs-beneficiario (código do beneficiário/convênio).
  • Não usa certificado digital (mTLS): o Banrisul autentica só por client_id / client_secret.
  • Operações suportadas no Sentus:
OperaçãoEndpoint Banrisul
Emitir (registrar) boletoPOST /boletos
Consultar boletoGET /boletos/{id}
Listar boletosGET /boletos
Alterar boleto (vencimento / abatimento)PATCH /boletos/{id}
Baixar boletoPOST /boletos/{id}/baixar
PDF do boletoGET /boletos/{id}/emitir
Webhook de cobrança (Banrisul → Sentus)POST /banrisul/webhooks/cobranca/{tenantId}/{portId}/{portAuth}

Pré-requisitos (cliente)​

Sem estes itens não é possível configurar

O cliente precisa ter convênio de cobrança ativo no Banrisul e acesso liberado ao Portal de Desenvolvedores.

  1. Convênio de Cobrança (Código de Beneficiário) ativo. Se não tiver, o cliente deve procurar a agência Banrisul de relacionamento.
  2. Cadastro no Banrisul for Developers: solicitar login e credenciais por e-mail para gestao_sistemas_cobranca_operacional@banrisul.com.br. O fluxo é feito uma vez para Sandbox e outra para Produção.
  3. Application criada no Portal, com a API de Cobrança (Boletos) associada.
  4. Convênio com permissão de uso via API habilitada (beneficiário "sem permissão" retorna erro mesmo estando ativo).

Código do beneficiário

Formato de 13 dígitos (ex.: 0010000001088). Na emissão o Sentus completa com zeros à esquerda; cadastre sempre os 13 dígitos.

Campos principais do portador:

CampoValor

ConvênioCódigo do beneficiário (13 dígitos)
Agência / ContaConforme contrato Banrisul
CarteiraDígito de controle (2 dígitos)

Juros, multa, desconto, protesto e baixa automática seguem o que o cliente combinou com o Banrisul.

Parâmetros (params)​

Exemplo para Produção:

api.ambiente=PRODUCAO
api.url.auth=https://api.banrisul.com.br/auth/oauth/v2/token
api.url.cob=https://api.banrisul.com.br/cobranca/v1/boletos
api.url.cobConsulta=https://api.banrisul.com.br/cobranca/v1/boletos/{id}
api.url.cobListar=https://api.banrisul.com.br/cobranca/v1/boletos
api.url.cobAlt=https://api.banrisul.com.br/cobranca/v1/boletos/{id}
api.url.cobBaixa=https://api.banrisul.com.br/cobranca/v1/boletos/{id}/baixar
api.url.cobPdf=https://api.banrisul.com.br/cobranca/v1/boletos/{id}/emitir
api.webhookAuth=CHAVE_DEFINIDA_PELO_SUPORTE
api.sentus=true
api.sentus.grantType=client_credentials
api.sentus.roles=boletos
api.client_id=COLE_O_CLIENT_ID
api.client_secret=COLE_O_CLIENT_SECRET

Exemplo para Homologação (Sandbox): mesmas chaves com sufixo Hom e host apidev:

api.ambiente=HOMOLOGACAO
api.url.authHom=https://apidev.banrisul.com.br/auth/oauth/v2/token
api.url.cobHom=https://apidev.banrisul.com.br/cobranca/v1/boletos
api.url.cobConsultaHom=https://apidev.banrisul.com.br/cobranca/v1/boletos/{id}
api.url.cobListarHom=https://apidev.banrisul.com.br/cobranca/v1/boletos
api.url.cobAltHom=https://apidev.banrisul.com.br/cobranca/v1/boletos/{id}
api.url.cobBaixaHom=https://apidev.banrisul.com.br/cobranca/v1/boletos/{id}/baixar
api.url.cobPdfHom=https://apidev.banrisul.com.br/cobranca/v1/boletos/{id}/emitir
api.webhookAuth=CHAVE_DEFINIDA_PELO_SUPORTE
api.sentus=true
api.sentus.grantType=client_credentials
api.sentus.roles=boletos
api.client_id=COLE_O_CLIENT_ID
api.client_secret=COLE_O_CLIENT_SECRET
Atenção
  • {id} é literal: o Sentus substitui pelo identificador do boleto (nosso número).
  • O Sentus escolhe a URL pela situação do portador: Homologação usa as chaves *Hom; Ativo usa as de produção. Preencha as duas famílias se o cliente vai passar pelas duas etapas.
  • api.sentus.roles deve ser exatamente boletos.
  • Sem api.url.cob* (ou *Hom) do ambiente ativo, a operação falha com "Url de ... inválida".

Homologação em Produção​

Antes de operar em produção, o Banrisul exige homologação:

  1. Na primeira chamada de registro em produção, enviar "ambiente": "T" no payload (somente no endpoint de registro).
  2. Emitir 5 boletos com sucesso em cenários variados que o cliente usará.
  3. Enviar requisições, retornos e PDFs dos 5 boletos para gestao_sistemas_cobranca_operacional@banrisul.com.br.
  4. Aguardar a liberação do Banrisul para operar em produção.

Regras de leiaute do boleto: papel mín. 50 g/m², formato envelope (95–108 mm × 170–216 mm), fundo branco com impressão preta ou azul, e usar a linha digitável retornada pelo banco no registro.

Webhook de cobrança (opcional)​

Para o Sentus ser avisado de pagamentos/baixas, o Banrisul precisa chamar:

POST https://<host-sentus>/banrisul/webhooks/cobranca/{tenantId}/{portId}/{portAuth}
ParâmetroOrigem
tenantIdIdentificador do tenant do cliente
portIdID do portador cadastrado
portAuthValor que o suporte define em api.webhookAuth no params do portador (texto aleatório). Precisa ser idêntico ao usado na URL; se faltar ou diferir, o Sentus rejeita o webhook

A URL não usa token: a validação é feita pelo trio acima. O Sentus responde 202 e sincroniza o título pelo titulo.nosso_numero. A URL de destino deve ser informada ao Banrisul na configuração do webhook do convênio.

Erros comuns​

SintomaCausa provável
401 UnauthorizedToken expirado ou client_id/client_secret errados / de outro ambiente
404 código A6 ("Código do beneficiário inválido ou encerrado")Convênio incorreto, desativado ou inexistente
Beneficiário "sem permissão"Convênio sem liberação de API: acionar o Banrisul
"Url de ... inválida"Falta a chave api.url.* do ambiente ativo no params
Boleto não registra em produçãoHomologação (ambiente=T) ainda não concluída
